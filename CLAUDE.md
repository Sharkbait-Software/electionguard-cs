# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a C# implementation of the [ElectionGuard](https://www.electionguard.vote/) end-to-end verifiable voting protocol (spec version `v2.1.0` — see `CryptographicParameters.VERSION_DEFAULT`). Code comments throughout reference spec section numbers (e.g. `§3.1.1`, `Verification 1`-`9`) — when in doubt about *why* a computation is shaped a certain way, the section number in the nearby comment is the source of truth, not the variable names. The spec serves as the source of truth for all operations contained within, so always verify changes against the spec.

## Build & Test

All projects are buildable and testable using the dotnet cli standard commands.

## Architecture

The following projects either currently are or will exist in this repository:

1. ElectionGuard.Core - This is the core cryptographic primitives used by everything else. This needs high test coverage, high reliability, and is the core purpose for the project. It will be used by other projects to build the end to end workflows, but all of the cryptography and math lives here.
2. ElectionGuard.Administration - This project will be focused on adminstering an election guard election. Allowing guardians to communicate with each other, generating the encryption record, collecting encrypted ballots, and orchestrating the decryption before finally creating an Election Record (the final output of ElectionGuard).
3. ElectionGuard.Verifier - The verifier project (S10b-14): `src/ElectionGuard.Verifier`, the `egrecord` command line (Spectre.Console.Cli, strict parsing, as `egperf`) over Core's record API. `egrecord verify <path> [--profile full|guardian|ballot] [--locator <device>/<position>]... [--parallelism N] [--checkpoint path] [--signature-policy report|require] [--trust key.pem]... [--json]` runs `ElectionRecordVerifier.VerifyAllAsync` and exits 0 passed and complete, 2 passed but incomplete (a newer format minor, R-2), 1 failed (a finding, a record the reader refuses at open, or a record value or manifest that does not decode), 3 a usage or I/O error; output is UTF-8 without a BOM whether or not it is redirected: `Main` puts a UTF-8 writer straight over a redirected standard output or error, so the bytes never depend on `Console.OutputEncoding` (which cannot always be set, and a redirected `--json` on Windows otherwise went out in the OEM code page, where the § of a message is the control byte 0x15), and sets a terminal's code page to UTF-8; `Program.Run` is the command tree without that set-up; `digest`, `convert <source> <destination> --encoding protobuf|json` (a `.zip` destination is a zip), `diff` (0 equivalent, 1 different), `prove <path> <confirmation code>` (finds the ballot with `ElectionRecord.FindBallotsAsync`, runs the ballot-correctness profile and checks its two inclusion proofs) and `show`. A locator is the device's directory name and the 1-based position (`regular-<H_DI hex>/3`). Its tests (`test/ElectionGuard.Verifier.UnitTests`) run every command over the committed golden records in process (`Program.Run` under Console.SetOut), plus one as a child process with stdout redirected, in a code-page-437 console and (on Windows, `DetachedProcess`) with no console at all, the only ones that see the bytes.
4. `perf/` - Performance testing. `ElectionGuard.Perf.Cli` (`egperf`) runs a scenario end to end -
   generate, encrypt, aggregate, decrypt - with per-phase timing, allocation and GC metrics, checks
   the decrypted tally against a known expected tally, and appends one JSON line per run to
   `perf/results/<machine>.jsonl`. `ElectionGuard.Benchmarks` is a BenchmarkDotNet project for
   function-level numbers. See `perf/README.md`. The harness streams in chunks because encrypted
   ballots are ~50 KB each and cannot be held in memory at scale; scenario JSON under
   `perf/scenarios/` controls which phases run and their time budgets, so a phase that is
   impractical today becomes practical by editing configuration rather than code. The optional `writeRecord` and
   `verifyRecord` phases write the run as an EGRF record and verify it with `VerifyAllAsync` (scenario
   `smoke-record`; off, they leave a scenario's config hash unchanged), and the `serialization` sub-benchmark
   measures the record's item codec.

Other related projects that will eventually exist that we need to prepare for:

1. Ballot encryptors - Encrypted ballots in reality may be generated in different languages and runtimes since they may come from different sources. Devices could run C#, C++, Rust, or any other language, or it could even be a browser running something like Javascript. Because of that, the project must be prepared to handle ballots encrypted in any language, and therefore we will implement encryptors in multiple languages. These encryptors will be benchmarked and be testable against a unified testing system.
2. Election Record Publish - The final election record must be distributable online. We will probably take some opinions on how that should be done, and may show an example or provide a platform for this purpose.

For the current stuff so far we have:

Two projects matter: `src/ElectionGuard.Core` is the library; everything else (`ElectionGuard.InMemory.Console`, `ElectionGuard.Verifier`, `ElectionGuard.Testing.Cli`, the unit test projects) is a consumer or fixture generator. There is no persistence layer, network layer, or UI — this is a pure crypto/protocol library operated by driving it from a `Program.cs` (see `src/ElectionGuard.InMemory.Console/Program.cs` for the canonical full pipeline).

The library models the ElectionGuard protocol as a straight-line pipeline, and the folders under `ElectionGuard.Core` mirror its phases:

1. **`Crypto`** — the math primitives everything else is built on: `IntegerModP` / `IntegerModQ` (structs wrapping `BigInteger`, auto-reducing mod the election's `P`/`Q`), `EGHash` (the spec's HMAC-SHA256-based hash, §5.2), and `ElectionGuardRandom`. Alongside these sits the Note 3.5 acceleration — `MontgomeryContext` (CIOS Montgomery multiply over `ulong` limbs), `MontgomeryModP` (Z_p in Montgomery form), `PowRadix` (a fixed-base comb table of powers of one base) and `PowRadixRegistry` (the opt-in store of those tables). Table-free exponentiation (`MontgomeryModP`'s table-free path and `SubgroupMembership`'s batch test) runs on `Avx512Montgomery` when `Avx512F.IsSupported` and p is at most 4096 bits: an "almost Montgomery" multiply over 80 52-bit digits held in 10 `Vector512` registers, with values kept redundant in [0, 2p) until converted out, so compare with `IsOne`, never digit-for-digit with `One`. .NET has no IFMA intrinsics, so each 52x52-bit digit product is split exactly into high and low halves by double-precision FMAs (a round-toward-negative-infinity FMA against 2^104, a subtract, a second FMA), and the halves' bit patterns are added into the integer accumulator with a fixed, operand-independent bias that is subtracted once at the end (`FinalBias`); the class remarks carry the exactness argument, so change the constants or rounding only with it in hand. Otherwise it falls back to the scalar `MontgomeryContext`; set `DOTNET_EnableAVX512F=0` to test that path, and `[Avx512Fact]` tests skip there. Its multiply, `Avx512MontgomeryKernel.cs`, is unrolled by hand over 10 named accumulator locals (the JIT keeps those in registers, not a span or array); its 10 per-vector copies must stay identical apart from their index. `PowRadix` picks its representation at build time: on AVX-512 its entries are the engine's 52-bit digits, one per `ulong` (640 bytes), otherwise scalar limbs (512 bytes); `PowRadix.Build(..., allowAvx512: false)` forces the scalar table in tests. `IntegerModP.PowModP` deliberately does **not** consult any of it and must stay that way; the acceleration is reached only through `MontgomeryModP`. `EGParameters` is a process-wide static holder for the active `CryptographicParameters` + `GuardianParameters` + `ParameterBaseHash`, defaulting to the spec's v2.1.0 parameters with no setup required — `EGParameters.Init(...)`/`EGParameters.OverrideScope(...)` exist only to swap in a different parameter set (e.g. to test that `ParameterVerification` rejects a record claiming different parameters). Arithmetic throughout Core reads parameters from `EGParameters` (`EGParameters.P`/`.Q`/`.G`), never from an `EncryptionRecord`/`GuardianRecord`'s own `CryptographicParameters` — that value is only a claim the record makes about its parameters, meaningful solely as the thing `ParameterVerification` (Verification 1) checks against `EGParameters`.
2. **`KeyGeneration`** — `Guardian` runs distributed key generation: each guardian generates Schnorr-proved key pairs, encrypts key shares to every other guardian (`EncryptShares`), decrypts the shares it receives (`DecryptShares`), and verifies the resulting `GuardianRecord` against the other guardians' public commitments (`Verify`). Guardian indices are 1..n (`GuardianIndex` rejects anything below 1: a share for index 0 would be P_i(0) = s_i, the secret key); `EncryptShares` takes exactly the other n-1 guardians' views and `DecryptShares` exactly one share from each of them, addressed to this guardian, else `ArgumentException`. `Guardian.Verify(record, ownManifest?)` follows §3.2.2's steps: full Verification 1 on the record (1.A-1.F, so the `GuardianRecord` carries `ManifestFile` and `ElectionBaseHash`), then the H_G comparison (eq. 27, keyed with H_B; `Guardian.ComputeGuardianRecordHash`), Verifications 2 and 3, and every share against its sender's commitments for i = 1..n (eqs. 28/29); the H_G and share failures throw `KeyCeremonyException` with the step and the offending guardian, as does (at step 1) a peer view this guardian holds that lacks exactly k commitments of each kind. This is a threshold scheme (`GuardianParameters.N`/`K`, defaulting to 3-of-2 and settable via `new GuardianParameters(n, k)`) — no single guardian's secret key can decrypt anything alone.
3. **`BallotEncryption`** — `BallotEncryptor.Encrypt` takes a plaintext `Ballot` + the election's `EncryptionRecord` and produces an `EncryptedBallot`: ElGamal-encrypts every selection and every supplemental field the contest declares (see below), generates the disjunctive Chaum-Pedersen proofs that each ciphertext encrypts a value in its valid range, and threads a per-ballot confirmation-code chain (`ChainingField`/`ConfirmationCode`) so ballots can be provably ordered/chained on a device. **Ballot chaining** (§3.4.4, §4.1.4, §3.7; G19/G37): every `EncryptedBallot` carries the 36-byte `ChainingField` B_C its confirmation code was hashed with (the ballot item's `chaining_field`, 36 bytes; `BallotStructure` requires it), as `PreEncryptedBallot` already did. `DeviceChain` is one device's chain (`DeviceChain.ForPreEncryptedBallots` for a pre-encrypted ballot device): encrypt through `BallotEncryptor.EncryptNext`, or pass `PreviousConfirmationCode` and `Append` each ballot (cast or challenged; it refuses another device's ballot or a field that does not fit its position); `Close()` returns the §3.7 `DeviceChainRecord`: device id, H_DI, ballot kind, mode, the confirmation codes in order, and under simple chaining H_0, the final input byte array and the closing hash (eqs. 74/78/77; 117/120/118 for pre-encrypted ballots, eq. 120 in the 69-byte body form per user decision Q4). An empty simple chain cannot be closed (eq. 78 needs H_ℓ). `ChainingField` holds the formulas (`InitialHash`, `Closing`, `ClosingHash` and their pre-encrypted forms) (the record carries it as the device section's header and close, `DeviceMapper`). A plaintext ballot it refuses (unknown or repeated contest, wrong option set, a negative selection, write-ins outside [0, `Contest.WriteInFieldCount`], contests other than its ballot style's) throws `InvalidBallotException` (an `ArgumentException`). A selection above R is not refused: it overvotes the contest. **Supplemental fields** (§3.1.3 p.19, §3.3.9; user decisions Q1-Q3, Q11-Q19): each `Contest` declares `SupplementalFields` (kind: overvote, null-vote or undervote indicator, undervote difference count, write-in count; at most one per kind), each with its own option index continuing after the options (m+1, m+2, ... in declaration order, enforced by `Manifest.Validate`). There is no counts-toward-limit flag (Q14): a field is declared ("tracked") or not, and every declared field takes part in the relations its kind calls for. Write-ins always count toward the limit like selections (Q13), so a contest that offers write-in fields must declare the write-in count. `Contest.VerifiableFields()` lists options then fields; the tally, decryption and Verifications 9-11 walk it. The voter gives only selections and `NumWriteinsSelected`; the encryptor derives the fields from s (the selections) and w (the write-ins). Each field is encrypted under its own nonce xi_{i,j} (eq. 33; `EncryptionNonce` has no j-less form), range-proved (0..1 for indicators, 0..L for the difference, 0..`WriteInFieldCount` for write-ins, with ind_o in the challenge), listed in `EncryptedContest.SupplementalFields` by label and hashed into chi after the options in manifest order (eq. 70; only declared fields). Q15's relations, each over the product of the options' and write-in count's ciphertexts and the declared fields' terms only (L times a field = its ciphertext raised to L, footnote 42): (1) the contest's `Proofs` (eq. 62 format) show s + w + L*overvote + undervote indicator in 0..L; (2) `UndervoteDifferenceProof`, present iff u is declared, is a one-value proof (Note 3.4, set {L}) that s + w + L*overvote + u = L, challenge H_q(H_I; 0x24, ind_c, ind_o(u), A, B, a, b); (3) `NullVoteProof`, present iff the null-vote indicator is declared, is a range proof that s + w + L*overvote + L*null is in 0..L (the overvote term since Q17, as in (1) and (2) only where that indicator is declared), challenge H_q(H_I; 0x24, ind_c, ind_o(null), b(L,4), A, B, a_0, b_0, ..., a_L, b_L). (2) and (3) are not spec-defined, so not interoperable. The disjunctive indicator-consistency proofs of §3.3.9 are not implemented (Q2), so two inconsistent values still verify: an undervote indicator of 0 with s + w < L, and a null indicator of 0 with s + w = 0. On an overvote the L*overvote terms force both indicators to 0 ((1) and (3)). Pinned by `Verification7_InconsistentIndicatorsNoRelationCovers_Verify`, together with the inherent case that a null vote re-encoded as an encrypted overvote verifies. Pre-encrypted ballots carry no supplemental fields (§4.1) or contest data (p.66), and `Manifest.Validate` refuses a manifest that names a hash-trimming function (an election that uses pre-encrypted ballots) and declares supplemental fields, write-in fields or contest data, or names a function other than Ω1-Ω8 (S9; an open user question). **Contest data** (§3.3.10; G11, user decisions Q5-Q7): each `Contest` declares `ContestDataBlocks` (b_Λ, 0 for none, else 1 <= b_Λ < 2^24; there is no election-wide length). A contest that declares it carries an `EncryptedContestData` (C_0 as `IntegerModP`, C_1 of exactly 32·b_Λ bytes, C_2 = (c, v)) on **every** ballot: `BallotContest.ContestData` is exactly 32·b_Λ raw bytes or null, and null encrypts 32·b_Λ zero bytes (the empty string's encoding), so neither the field's presence nor its length shows whether write-in text was entered. `ContestDataEncoding` is the library's (non-spec, Q7) string encoding: b(len,4) ‖ UTF-8 ‖ zero padding, rejected (never truncated) when too long. `ContestDataEncryption` holds every derivation the encryptor, guardians and Verification 12 share: ξ (eq. 64), h (eq. 65), the KDF keys (eq. 66: block counter 1..b_Λ per Q6, constant length field b(b_Λ·256, 4), Label/Context `data_enc_keys`/`contest_data`), the 0x27 Schnorr proof (eq. 69) and the decryption (eqs. 104-106). Eq. (70) hashes b(C_0,512) ‖ C_1 ‖ b(c,32) ‖ b(v,32) after the fields. `BallotStructure` requires the field exactly where declared, C_1 of exactly 32·b_Λ bytes (`"N.structure"`). The 0x27 proof is checked by guardians before decrypting (§3.6.6), not by any numbered verification: the spec has none for it. It does not prove C_0 is in Z_p^r (C_0 = 0 passes with a = 0, and C_0 = -g^ξ whenever c is even), so the guardians and the administrator also require `SubgroupMembership.IsMember(C_0)` first, a library hardening the spec does not state and Verification 12 does not include; the ballot-nonce decryption of §3.6.7 makes the same check on C_ξB,0. **Ballot nonce** (§3.3.4; G17): every `EncryptedBallot` carries `EncryptedBallotNonce` (C_ξB: C_0 as `IntegerModP`, C_1 exactly 32 bytes, (c_B, v_B)), ξ_B encrypted to K-hat. `BallotNonceEncryption` holds eq. (35) h = H(H_I; 0x22, α_B, β_B), eq. (36) k_1 = HMAC(h, 0x01 ‖ "ballot_nonce" ‖ 0x00 ‖ "ballot_nonce_encrypt" ‖ 0x0100) (a one-byte counter and a two-byte length, as on the p.30 page image; not eq. 66's four-byte fields), the 0x23 Schnorr proof (eq. 38) and the decryption. ξ_B is 32 bytes, never reduced mod q. C_ξB is not an input to any contest hash or the confirmation code (eqs. 70, 71). `BallotStructure` requires it, C_1 of exactly 32 bytes (`"N.structure"`). `BallotEncryptor.BallotNonceEncryptionNoncesForTesting` fixes ξ-hat_B and u_B for the KAT.
4. **`Tally`** — `EncryptedTally.AddBallot` homomorphically accumulates encrypted ballots per contest/choice (ElGamal ciphertexts multiply to add plaintexts), each raised to its weight; `AddBallots` does the same for a batch across threads. Only ballots whose `EncryptedBallot.Status` is `Cast` are aggregated: `Challenged` and `Spoiled` ones are skipped, and `Unrecorded` (value 0, in memory only: what the encryptor leaves; the status, cast, challenged or spoiled, is recorded afterwards, once, with `RecordStatus`), any undeclared value, or a weight below 1 fails as `"9.structure"`. `Spoiled` (= 3, S10b-1, user decision S10b #4) is a submitted ballot that was neither cast nor challenged: it stays in its device's chain, counts for 5.A and 11.D, gets Verifications 5-8 like any ballot, is never tallied, and is not decrypted by this library's paths (the nonce path and V13/V14 accept only `Challenged`). That status test reads the requester's claim; what refuses a spoiled ballot relabelled `Challenged` is the guardian's view of the record, which holds spoiled ballots beside cast ones (user decision "Refuse spoiled too", 2026-10-09; see below). The election record's section seal and signatures protect the recorded status itself (S10b-6+). The enum values equal the election record's `BallotStatus` numbers. Decryption is the verifiable §3.6.5 protocol, in three rounds on `TallyGuardian` that a `TallyAdmin` mediates (there is no network layer; `TallyAdmin.Decrypt` drives in-process guardians, `TallyAdmin.Combine` takes the three rounds' messages from anywhere): `Commit` (M_i = A^{z_i} and the commitment hash d_i of eq. 88 over a fresh secret u_i), `Reveal` ((a_i, b_i), only once every participant's d_j is in), `Respond` (checks every d_j against its own A, B, indices and U, computes the eq. 90 challenge itself, returns v_i; single use, so u_i never answers two challenges). `Combine` re-checks every d_j, forms M (Lagrange, eq. 86), T, c and v, checks the proof before publishing (on failure Note 3.7's per-guardian checks name the guardian), and recovers each count by a baby-step giant-step search over `[0, the largest EncryptedAggregateChoice.MaximumCount]`. Protocol failures throw `TallyDecryptionException` with `OffendingGuardian`. `DecryptedTally` publishes ind_c, ind_o, t, T, c and v per option, supplemental fields included (under their labels and option indices). Eq. (88) encodes U in ascending index order (the spec does not say; the KAT oracle does the same). Contest data decryption (§3.6.6, G32) is the same protocol, on the same classes, for one ballot contest at a time: `TallyGuardian.CommitContestData`/`RevealContestData`/`RespondContestData` (each guardian first requires C_0 in Z_p^r and the field's 0x27 proof, and refuses with a `TallyDecryptionException` naming no guardian otherwise; m_i = C_0^{ẑ_i} with the ballot data key share; d_i and c are eqs. 99/101 keyed with H_I per Q5, in `ContestDataDecryptionHashes`), mediated by `TallyAdmin.DecryptContestData`/`CombineContestData`, which publishes `DecryptedContestData` (β, c, v and D; `DecodeText()` reads the Q7 encoding). Both decryptions run on the internal `VerifiableDecryption` engine (round-1 values, the d_j check and combination, responses, the proof check, Note 3.7 attribution) over `IDecryptionStatement`s (`TallyOption`, `ContestDataStatement`); a guardian holds one session of one kind at a time, and the other kind's reveal/respond refuses it. Guardians and Verification 12 recompute H_I from H_E and id_B. **Challenged ballots** (§3.6.7, G18) are opened through the ballot nonce, not the three rounds: §3.6.7 defines no proof of correct decryption for it (ξ_B is never published). `TallyGuardian.DecryptBallotNonce(ballot, record, publishedBallots)` first decides whether the request is authorized at all (user decision Q31, S9b; spoiled ballots added 2026-10-09, "Refuse spoiled too"): `publishedBallots` is a required `IPublishedCastAndSpoiledBallots`, the guardian's own view of the published record's cast and spoiled ballots (`PublishedCastAndSpoiledBallots`: per status, content-keyed hash sets of id_B, H_I and SHA-256(C_ξB,0), filled incrementally, bound to H_E; `FromRecord` skips challenged ballots and refuses one with no recorded status; `Add` refuses anything but cast or spoiled; `Add(status, id_B, H_I, C_ξB,0 bytes)` holds a sealed record item's raw values, for the record verifier, whose items with a value out of range have no `EncryptedBallot`), and a request whose id_B, H_I or C_ξB,0 matches any of them is refused with `BallotNonceDecryptionRefusedException` (`Reason` = `CastBallot`, or `SpoiledBallot` when only spoiled ballots match; `ForeignElection` for a view of another election), before any exponentiation with ẑ_i. `Match` returns a `PublishedBallotMatch` (the matching values, `BallotValueMatch` flags, per status). Only then does it require the ballot to be recorded `Challenged` (a sanity check only: `Status` is the requester's claim, and a cast ballot copied and relabelled passes it), well formed and keyed with the recomputed H_I (`ArgumentException`), then C_ξB,0 in Z_p^r and the eq. (38) proof (`TallyDecryptionException` naming no guardian), and return m_i = C_ξB,0^{ẑ_i} (`BallotNoncePartialDecryption`, one message; it does not touch a tally or contest data session). Trust model: everything in the request is a claim; the view is not, and a distributed guardian builds it from its own copy of the record, never from the administrator. It protects the ballots it holds, so decrypt challenged ballots once the record's ballots are final. It also refuses, by design, cast ballots selected for a risk-limiting audit, the other use §3.3.4 p.30 names for nonce decryption: an audit flow (deferred, Q22) needs its own authorization path, e.g. an audit-selection list committed after the record is final. The guardians decrypt no pre-encrypted ballot's nonce (Q35, S9c), and they know nothing of pre-encrypted ballots until those are recorded (Q33), so a printed pre-encrypted ballot not yet recorded, whose id_B, H_I and C_ξB are built as a regular ballot's (§4.2), would be answered here if wrapped as a challenged regular ballot: keeping such requests from the guardians is the deployment's and its recording tool's job (S9c carry-over; pinned by `PreEncryptedCastRecordTests.DecryptBallotNonce_UnrecordedPreEncryptedBallotWrappedAsChallenged_OpensIt_KnownExposure_S9b_1`; the user's sign-off is open as S9c-R1 in the tracker). `TallyAdmin.DecryptChallengedBallot(guardians, ballot, record, publishedBallots)` passes the view to each guardian; `CombineChallengedBallot` takes no view (the administrator is the party the check guards against) and re-checks the rest, takes a quorum (one message each, for this ballot, no zero m_j), forms β_B (eq. 108) and ξ_B, derives every field's ξ_{i,j} (eq. 33) and each contest data ξ (eq. 64), requires g^ξ to reproduce every α and C_0, finds σ in [0, the field's range bound] with β = K^{σ+ξ} (eq. 109), decrypts D (eqs. 110, 111), and publishes `DecryptedChallengedBallot` (per contest, its index and label: options and supplemental fields as `DecryptedChallengedField` (index j, label, σ, ξ_{i,j}), and contest data (ξ, D)), never ξ_B. Verification 13 finds the ciphertexts by the stated indices; Verification 14 checks the labels (14.A-14.D, presence checks as the spec words them) and then that each contest and field stands at its label's manifest index and in the list of its kind (`"14.structure"`, user decision 2026-10-10), so a mislabelled field fails 14.x, not 13.x (design §4.6). A nonce that reproduces nothing throws naming no guardian: a wrong m_i and a device that encrypted the wrong ξ_B cannot be told apart without a proof the spec does not define.
5. **`Verify`** — one class per protocol verification, mirroring the spec's numbered verification list (`ParameterVerification` = Verification 1, `GuardianPublicKeyVerification` = 2, `ElectionPublicKeyVerification` = 3, `ExtendedBaseHashVerification` = 4, `SelectionEncryptionIdentifierVerification` = 5, `SelectionEncryptionsWellFormedVerification` = 6, `AdherenceToVoteLimitsVerification` = 7, `ConfirmationCodeVerification` = 8, `BallotAggregationVerification` = 9, `TallyDecryptionVerification` = 10, `TallyContentsVerification` = 11, `ContestDataDecryptionVerification` = 12, `ChallengedBallotDecryptionVerification` = 13, `ChallengedBallotWellFormednessVerification` = 14; under `Verify/PreEncryption`, `SelectionVectorAccumulationVerification` = 15, `PreEncryptedConfirmationCodeVerification` = 16, `ShortCodeVerification` = 17, `UncastBallotEncryptionVerification` = 18, `UncastBallotContentVerification` = 19; see the pre-encryption bullet below). Verification 9 compares exactly the manifest's options and declared supplemental fields (a missing or extra tally key is `"9.structure"`, then `"9.A"`/`"9.B"`); 10 checks each option's (T, c, v, t) against its (A, B) with ind_c/ind_o from the manifest (`"10.structure"` if a label or published index does not match, then 10.A-10.C); 12 checks one ballot contest's `DecryptedContestData` against its (C_0, C_1, C_2) (`"12.structure"`, then 12.A-12.C); 8 is per ballot (`Verify(ballot, record)`: 8.A, 8.B over the ballot's own B_C, 8.D under no chaining, only the 0x00000001 identifier under simple chaining; the overload with a device hash and previous code adds 8.C and 8.E against them) and per device (`VerifyDevice`/`VerifyDevices`, over ballots or `DeviceChainLink`s so a streaming caller keeps no ballot; the walk is `DeviceChainWalk`, shared with 16's `VerifyDevice`, whose lettered checks run on the constant-memory `DeviceChainWalker` that the record verifier drives item by item: `Begin`/`Next`/`End` return the first failure of each step and the walk goes on, `Skip` marks an unreadable link, and its state exports for a checkpoint; the domain path keeps the O(N) code index only for its completeness checks, which a record's device section makes structural): `"8.structure"` unless the list names exactly the ballots of that device, each once, then 8.C (the recorded H_DI), 8.F (H_0), 8.D/8.E for each ballot in list order (B_C,j = 0x00000001 ‖ H_{j-1}), 8.G (the close); reordered, dropped or spliced ballots fail 8.E, a dropped last ballot 8.G (16.D-16.H the same for pre-encrypted chains). Only chaining modes 0x00000000 and 0x00000001 exist: `Manifest.Validate` refuses any other `ChainingMode` value (§3.4.4 leaves other modes to the manifest, and this model specifies none), so the `mode != None` branches mean simple chaining. Before S8, 8.D/8.E compared two values built from the same inputs (G37). 13 recomputes a challenged ballot's (α, β) from the released ξ_{i,j} and σ, its contest hashes and H_C (13.B over the ballot's own B_C, or, in the overload that takes a device hash and previous code, B_C formed from them as Verification 8 forms it; a contest left out, the RLA case, uses its hash recomputed from the encrypted ballot; a decrypted contest must release every field, so the selection-level subset of p.52-53 fails `"13.structure"`) and each contest data field from the released ξ (13.A, KDF counter 1-based per Q6; 13.A also requires g^ξ to equal the ballot's C_0, a library hardening the spec's 13.4-13.A leaves out: χ hashes the ballot's own C_0, so without it any ξ' with D' = C_1 ⊕ k(ξ') passed), after `"13.structure"` (status `Challenged`, `BallotStructure`, H_I, one release per field); 14 checks the decrypted ballot's labels against its ballot style and the manifest (14.A-14.D, options and supplemental fields alike, presence only; 14.B reads "uncast pre-encrypted ballot" in the spec, a copy of 19.B, and is applied to the decrypted challenged ballot, so a partial decryption fails it), then each contest's and field's (index, label) pairing and list against the manifest (`"14.structure"`, user decision 2026-10-10) and each value's range (14.E: 0..R, or the supplemental field's bound) and s + w <= L (14.F, write-ins counting per Q13), after `"14.structure"`; 11.D takes the contests of every submitted (cast or challenged) ballot. Failures throw `VerificationFailedException`, which carries a `SubSection` (e.g. `"1.B"`) matching the spec's lettered sub-checks — tests assert on this field, not just on the exception type. `ParameterVerification.Verify(EncryptionRecord)` / `Verify(GuardianRecord)` is the full Verification 1 (1.A-1.F, H_B against the record's `ManifestFile`); 1.E also requires the record's n and k to equal `EGParameters`'. Verifications 2 and 3 require exactly G_1..G_n (reported as 2.A / 3.A), and 2 requires exactly k commitments (2.A) and k+1 responses (2.B) per proof before indexing into them. Before any lettered check, Verifications 6, 7, 8, 16 and `EncryptedTally.AddBallot` (which Verification 9 reuses) call `BallotStructure.Require`: the ballot style exists, the ballot lists exactly its contests, each once, and each contest exactly the manifest's options and declared supplemental fields, each once, plus contest data exactly where declared, the encrypted ballot nonce with a 32-byte C_1 and a 36-byte chaining field (for a pre-encrypted ballot: the manifest's contest index, and m option vectors plus L null vectors of m entries each). The spec letters no sub-check for this, so it fails as `"N.structure"` (`"6.structure"`, ..., `"9.structure"`, `"16.structure"`); without it a contest copied verbatim passed Verifications 5-9 and was tallied twice. Its pass path allocates nothing. Verification 5.A needs the identifiers of every submitted ballot: `SelectionEncryptionIdentifier` compares by content, and a caller that sees ballots in batches feeds one `SelectionEncryptionIdentifierSet` (the perf harness does, across chunks). The record verifier uses `SpillingIdentifierSet` instead (design §6.5): 8 bytes per ballot, the first 8 bytes of SHA-256(k ‖ id_B) under a secret per-run key k (so a publisher cannot aim two ballots at one prefix, and skewed id_B values do not skew the runs), sorted runs spilled to disk beyond its budget, a k-way merge for colliding prefixes, then an exact confirmation pass over the ballot items naming both locators. 6.B/6.C and 7.B/7.C accept 0 (Z_q = {0..q-1}). Verification 6 checks every supplemental field's range proof (6.A-6.D, its own bound); Verification 7's 7.A covers every field's alpha and beta, 7.B-7.D the combined selection-limit proof, and the undervote difference and null-vote proofs' Z_q and challenge checks report as 7.B/C and 7.D with messages naming the proof (a missing, unexpected or wrong-length one is `"7"`). V7 computes the three relation ciphertexts in one engine representation (`RangeProofChallenge.RelationCiphertexts`: each input converted in once, the overvote power shared by all three, each output converted out once). A null proof list or a null entry in one (only a ballot built in memory can hold either: the record decoder has no null) fails like a list of the wrong length, `"6"` or `"7"`, after 6.A/7.A; a record item reaches the same codes with a proof of the wrong count (a whole number of pairs passes D1) or an omitted relation proof (`(omittable)`). A record item without C_ξB, or without contest data where b_Λ > 0, decodes (neither field has a width option) and fails `BallotStructure`.
6. **`Models`** — plain data types plus a family of hash-derived value types (`ParameterBaseHash`, `ElectionBaseHash`, `ExtendedBaseHash`, `ContestHash`, `ConfirmationCode`, etc.) whose constructors *compute* the hash from their inputs (per the spec's hash chain) rather than being simple property bags — treat these constructors as the spec formula, not boilerplate.
7. **`Serialization`** — what remains outside the record. S10b-16 retired the protobuf-net and System.Text.Json ballot, record, device-chain and pre-encrypted serializers (`IEncryptedBallotSerializer`, `JsonElectionRecordSerializer`, their `Protobuf*` DTOs and JSON converters, `StrictBase64`, `EncryptedBallotShape`) and the protobuf-net package: a ballot travels, and a record is stored, as record items (item 8). `ManifestSerializer` is the one manifest format (see "Working in this codebase"). `StrictJson.RejectAmbiguity` (no BOM, no repeated member, well-formed UTF-8, no lone-surrogate escape, nesting at most 64) guards every JSON document this library reads: the manifest and the record's JSON lines. Published values decode strictly: `IntegerModP.FromCanonicalBytes` (exactly 512 bytes, below p), `IntegerModQ.FromCanonicalBytes` (exactly 32 bytes, below q), and `SelectionEncryptionIdentifier` and the hash values (`ContestHash`, `ConfirmationCode`, `SelectionEncryptionIdentifierHash`, `VotingDeviceInformationHash`, `ParameterBaseHash`, `ElectionBaseHash`, `ExtendedBaseHash`) `.FromCanonicalBytes` (exactly 32 bytes, kept as read, so 1.E/1.F/4.A still check a claim) throw `NonCanonicalEncodingException`, a deserialization error rather than a verification sub-section. The reducing `IntegerModP(byte[])`/`IntegerModQ(byte[])` constructors are for internal arithmetic only (they would read alpha + p as alpha and q as 0): a new decoder of published values uses the strict path or the record's raw values, never them. No output carries a nonce: no schema field is named for one (`RecordCompletenessTests.NoSchemaField_CanHoldASecret`, a check of names only), no option or field nonce occurs in the bytes or the JSON line `RecordItemCodec` writes for a regular or cast pre-encrypted ballot (`RecordItemCodecTests`' byte search; ξ_B in the challenged-ballot item: `ChallengedBallotDecryptionTests`), and the domain's `EncryptionNonce` members are `[JsonIgnore]` against ad hoc dumps. `EncryptedBallot.EncryptionTimestamp` (G40, §3.7 "the date and time of the ballot encryption") is optional, UTC to the millisecond from the encryptor's `TimeProvider` (constructor parameter, default `TimeProvider.System`), the item's `encrypted_at` (decode rule D3: 1970 to 9999, whole milliseconds; in a JSON line only the formatter's form, `Z` with no fraction or exactly three digits, provisional rule (d)), and not a hash input (eq. 71), so only the record's root and signatures protect it.
8. **`RecordFormat`** — the election record, EGRF v2 (S10b). The design and its rationale are `docs/spec-compliance/2026-10-08-election-record-design.md` (its §8.3 "As built" notes describe each class); the normative rules, drafted as a specification, are `docs/spec-compliance/egrf-v2-spec.md`. What a contributor must keep:
   - **Schema.** `proto/electionguard/egrf/v2/egrf.proto` at the repository root is the one normative schema, shared by every implementation. Core compiles it at build time (Google.Protobuf, and Grpc.Tools as a build-only dependency) into **internal** types in `ElectionGuard.Core.RecordFormat.Protobuf`, aliased `Pb` (not `...Core.Record...`: that namespace would hide xUnit's `Record` in every test). Changes are append-only: `EgrfSchemaLintTests` enforces the profile's schema rules S1-S8 on the compiled descriptor and diffs it against `test/egrf/schema.json` (`EGRF_WRITE_SCHEMA=1` accepts an append-only change). The custom options `width`, `width_multiple` and `omittable` use the draft numbers 50001-50003 until they are registered (a user action, S10b-18).
   - **Canonical form.** Every item is stored as its one canonical encoding (wire rules W1-W8, decode rules D1-D6), decided by `CanonicalProtobuf.Check` (Method B, then Method A to name the rule). Range (≥ p, ≥ q) is never a format rule: the internal mappers (`RecordFormat/Mappers`) decode raw (`RawZp`/`RawZq`, never reducing) and report a value out of range as a `RecordFinding` under design §4.8's code (`RecordValueRanges`), with no domain object, and verifications reach record items through `RecordItemGate`. Encrypted items carry manifest indices, not labels; the device id is the section header's; final-phase items name a ballot by locator and H_I. Two enums are closed (`SectionType`, NQ-7; `DeviceKind`, NQ-9: an undeclared value is D2 at any reader age); there are no vendor sections (vendors extend only the manifest).
   - **Adding a member.** A public member added to a recorded domain type fails `RecordCompletenessTests` until it is mapped to a schema field or excluded explicitly; this replaced the protobuf-net "add it to the DTO too" rule.
   - **Public surface.** One ballot at a time: `RecordItemCodec` (the canonical item bytes or its proto3 JSON line; a non-canonical item is `NonCanonicalEncodingException`, a value out of range a `VerificationFailedException` under its code; the record holds a ballot as re-encoded from the domain ballot, with no bytes-level append, so an item sent without the free-text `ballot_ref` is stored with the hex of id_B in it). Writing: `ElectionRecord.Create(directory, encoding)` → the phase-gated `ElectionRecordWriter`: `WriteSetupAsync` (the manifest bytes stored as given) → `OpenDeviceAsync`, `DeviceSectionWriter.AppendAsync` (recorded status, `BallotStructure`, the chaining field; never proofs), `CloseAsync` → `SealVotingAsync` → `SealAggregatedAsync(tally, requests)` → only after R_aggregated (Q36) the decryptions and uncast releases → `CompleteAsync`; `ElectionRecord.ResumeAsync` repairs torn tails and continues; `AddAttestationAsync`/`AddRecordSignatureAsync` (`ecdsa-p256-sha256`). Reading: `ElectionRecord.OpenAsync` (a directory or `.zip`, protobuf segments or JSON lines; layout, version and presence checked at open), `ComputeTocAsync` (a claimed TOC is never trusted), `ConvertAsync` (keeps every root), `DiffAsync`. Record-level failures are `VerificationFailedException` with an R-code (`RecordCodes`).
   - **Verifying.** `ElectionRecordVerifier.VerifyAllAsync` runs Verifications 1-19 and every record rule (profiles `Full`, `GuardianPreliminary`, `BallotCorrectness`, `Custom`). Nothing a record's publisher controls may make it throw: every fault is a finding under its code, and a verification that could not run over every item it covers is `NotEvaluable`, never `Passed`. Findings are collected and ordered deterministically, so parallel, resumed and single-threaded runs and all four representations give one report. Guardians decrypt a tally read from a record only through `VerifyAggregatedAsync` → `VerifiedAggregate` → `TallyAdmin.Decrypt(guardians, aggregate)`, and check challenged-ballot requests against `aggregate.PublishedBallots` (Q31). The device pass cuts the device sections into batches of 16 items per worker (and `BatchBytes`), each ending at a barrier after which the leaves and closes are taken in record order, reads the next batch while the workers run unless a checkpoint or an early stop may follow, and passes `MaxDegreeOfParallelism` through (1 is single-threaded). Verification 9 partials cross threads, checkpoints and machines only in standard form (`ExportStandardForm`), never as a `ModPProduct`. A checkpoint (`CheckpointPath`) is local trusted state, never to be accepted from a third party.
   - **Conformance artifacts.** `test/egrf/vectors/` (`EGRF_WRITE_VECTORS=1` rewrites them; review the diff), the golden and negative records under `test/egrf/records/` (`EGRF_WRITE_RECORDS=1` regenerates them, `=missing` adds new ones only), and `test/egrf/egrf_ref.py`, an independent Python 3 reader written from the design and the `.proto` alone, which `EgrfGoldenRecordTests` require to agree with this library record by record and on seeded mutations. A disagreement is a C# defect or a design gap, never a vector to edit. Reader rules that rest on an implementation choice awaiting the user's sign-off carry `basis` in `index.json` and are marked provisional in the spec draft. The draft's schema appendix is generated by `test/egrf/spec_tables.py` from `schema.json` and the `.proto`'s field comments, continuation lines included; `EgrfSchemaLintTests` runs its `--check`, so rerun the script after a schema or comment change.

## Working in this codebase

- `IntegerModP`/`IntegerModQ` read `P`/`Q` from `EGParameters`, which defaults to the spec's v2.1.0 parameters — no initialization is required to use them. Only call `EGParameters.Init(...)`/`EGParameters.OverrideScope(...)` when a test deliberately needs a non-default parameter set.
- When encrypting or verifying, always use `EGParameters.P`/`.Q`/`.G`, never `encryptionRecord.CryptographicParameters.*` or `guardianRecord.CryptographicParameters.*` — those are untrusted claims from the record, only meant to be checked against `EGParameters` inside `ParameterVerification`.
- `GuardianParameters` defaults to N=3, K=2; pass `new GuardianParameters(n, k)` for other thresholds. `ElectionFixtureBuilder.CreateGuardianSet(n, k, manifestFile)` builds a matching guardian set; the manifest file (default: `CreateMinimalManifest()`'s) goes into the guardian record, whose H_B every guardian checks. `EncryptionRecord` carries `ParameterBaseHash`, `ManifestFile` (the bytes H_B is computed over) and `ElectionBaseHash` (§3.7). Its `Manifest` is **derived**: setting `ManifestFile` parses and validates it with `ManifestSerializer` (the library's one manifest format: case-sensitive camelCase JSON, no BOM or repeated member (known or not), known members strict (types, required members, no null where required, no null entries; kinds by exact name), and **unknown properties ignored** at every level (user decision NQ-1: the manifest is where vendors add data; they stay in the bytes, so H_B binds them) but still checked as text (well-formed UTF-8, no lone-surrogate escape, nesting at most 64 levels, so acceptance never depends on which properties a reader knows), near misses of a member's name included (another case, or with `_`/`-`: member names are matched exactly, so these are unknown properties too; user decision R-3, "Ignore them too", removed S10b-A's refusal); optional informational election facts `ElectionName`, `ElectionDate`, `ElectionType`, `Jurisdiction`, `Location` (§3.7, NQ-4), omitted from the written form when null; written compact in declaration order, without unknown properties; see its remarks), and there is no other way to give a record a manifest, so what Verifications 6-14, the encryptor, pre-encryption and the tally read is what 1.F checked (S10a; S2 review R1). Build a record's file with `ManifestSerializer.ToManifestFile(manifest)`; to give a test record another manifest, give it another file (its H_B claim then fails 1.F, which is the point). `ElectionFixtureBuilder.CreateEncryptionRecord(set, manifest, file)` throws unless `manifest` is what `file` holds, so a test that changes its manifest object after building the file must rebuild the file. The record copies the file's bytes when it is built; treat `record.ManifestFile` and `record.Manifest` (a mutable object graph) as read-only, since nothing re-checks the parse against the bytes afterwards (only `ManifestValidationTests`' reorder probe mutates it, deliberately). A file need not be in the written form to be read (H_B hashes it as it is); the perf harness, the corpus command and `Testing.Cli` write the written form, which for every committed manifest is the bytes `PerfJson.LineOptions` wrote before, so `manifestHash` did not move. `GuardianRecord` carries only the file (no parsed manifest; the guardians check H_B over it). The KAT records keep the oracle's H_B/H_E (over `{"election":"kat"}`) as claims beside a file of the shaping manifest; they never run 1.F.
- `test/data/*` holds the committed manifests and plaintext ballots (camelCase JSON, read with System.Text.Json; see `test/data/famous-names/`) — `ElectionGuard.Testing.Cli` generates equivalent fixtures programmatically via Bogus for larger test scenarios. Encrypted data is published only as an election record (the golden records under `test/egrf/records/`).
- `BallotEncryptor.EncryptContest` MUTATES the plaintext ballot it is given: on an overvote it sets
  every `BallotChoice.SelectionValue` to 0. Anything computing an expected tally must do so *before*
  encrypting. The overvote rule is the spec's (§3.3.5, §3.1.3 p.18, §3.3.9 p.38; G10): the contest is
  overvoted when s + w (selections plus write-ins, which always count, Q13) exceeds L, or when any one
  option exceeds R. It then contributes nothing: every option encrypts 0, the write-in count 0 (Q12),
  the overvote indicator 1, the null-vote and undervote indicators 0 (Q3, Q11) and the undervote
  difference count 0 (Q15: s + w + L*overvote + u = L). A contest that declares u but not the overvote
  indicator has no overvote term, so there u = L on an overvote (Q18: with no tracked overvote field there
  is no published overvote, and the neutralized contest is a blank one). A null vote
  (s + w = 0) has undervote indicator 1, difference L and null indicator 1; a write-in-only ballot is not
  a null vote. `ExpectedTallyAccumulator`
  re-derives this from the decision text rather than copying the encryptor, and produces the supplemental
  totals, which `TallyComparer` checks; keep the two independent.
- Use `MontgomeryModP.PowModP` for exponents that are full-width elements of Z_q — nonces,
  challenges, responses, secret keys. It is ~2.5x `IntegerModP.PowModP` on its own (~10x with AVX-512) and ~26x once
  `BallotEncryptor.PrecomputePowerTables` has been called, because the bases are g, K and K-hat.
  Do **not** use it for small public exponents (a ballot weight, a guardian index, a loop counter):
  it walks the full width of Z_q regardless of the exponent's value, deliberately, so that the work
  never varies with a secret. `BigInteger.ModPow` scales with the exponent's magnitude and wins
  there, as does a narrow-window Montgomery exponentiation over just the exponent's own bytes, which
  is how `ModPProduct.MultiplyPower` raises a ballot weight.
- The tables are opt-in and caller-owned. Nothing is built until someone calls
  `BallotEncryptor.PrecomputePowerTables`, and they are keyed by base, so a process that moves
  between elections should `PowRadixRegistry.Clear()` rather than accumulate a set per election.
  Exponents that are not in Z_q (the `x^q mod p` subgroup checks in Verifications 2, 6 and 7) must
  use the `BigInteger` exponent overload: reducing q into `IntegerModQ` makes it zero and turns
  those checks into `x^0 = 1`, which passes for everything.
- Verification 6.A is normally decided exactly, for free, on the squaring chains the
  range-proof checks walk anyway: q = 2^256 - 189, so for x != 0, x^q = 1 iff x^(2^256) = x^189,
  and `MontgomeryModP.PowVariableTimeMontgomeryCheckingMembership` carries alpha's and beta's chains
  to 2^256 and gathers x^189 from them (`TryGetChainMembershipShape` gates this on q = 2^t - c with
  few set bits in c). That reorders work but must not reorder failures -- 6.A for any value is
  reported before any other lettered check (the `"6.structure"` precondition still comes first) --
  so `VerifyFused` runs only when every structural check (proof count, Z_q ranges) passes;
  otherwise `VerifyInOrder`, the original order, runs. The fused path stops at the first 6.D and
  runs the batch test below over the whole ballot before reporting it. Tampering alpha or beta also
  breaks its proof, so only a forged *valid* proof for a non-member (`NonMemberRangeProof` in the
  tests: -alpha with even challenges) shows the fused check is applied at all.
- Verification 7.A checks every selection's alpha_i and beta_i (p.37: subscript i, no overbar; user
  decision Q8), not the contest aggregates: two non-members can multiply to a member. V7's proof
  chains are the aggregates', so it cannot read membership off them; it runs the batch test below
  over the ballot's selections first, before any other 7.x check. The aggregates need no test of
  their own (Z_p^r is closed under multiplication). This costs V7 one batch test per ballot (S3:
  smoke VerifyBallots 0.366 -> ~0.47 ms/ballot, xsmall 6.66 -> ~7.4).
- The batch test, `SubgroupMembership.IndexOfFirstNonMember`: an exact Jacobi-symbol pass, then a
  probabilistic batch test (random 128-bit exponents, one multi-exponentiation, one `^q`). Its
  soundness rests on p - 1 = 2·q·r' with r' a large prime, which holds for the spec's parameters
  only, so it falls back to exact per-value checks under any other parameter set. A unit test pins
  that factorization. Its loops are `AggressiveOptimization`: runs of a few thousand ballots are too
  short for tiered compilation to promote them.
- `MontgomeryModP.PowModPVariableTime` raises one base to several exponents over one shared
  squaring chain (Yao/BGMW with right-to-left sliding windows, odd digits, w = 4), walking
  x^(2^i) once and keeping only the current power plus 2^(w-1) buckets per exponent. It is
  **variable-time and verifier-only**: its work depends on the exponents' digits, so it is safe only
  for public values such as the proof challenges c_j of Verifications 6 and 7. Never call it from
  `BallotEncryption`, `KeyGeneration` or `Tally`, or with a nonce or secret key.
- Verifications 6 and 7 compute their commitments through `RangeProofChallenge`, which multiplies
  g^v by alpha^c (and K^w by beta^c) in one engine representation and writes the bytes straight into
  the hash input. Its helpers (`PowRadix.PowMontgomeryInto`, `MontgomeryModP.PowVariableTimeMontgomery`)
  return values in the active engine's own form -- AVX-512 digits or scalar limbs -- so only combine
  them with values in that same form.
- `EncryptedAggregateChoice.A`/`B` are backed by `ModPProduct`, a running product in the active
  Montgomery engine's form. Each factor is multiplied in without being converted into Montgomery
  form, so the accumulator carries an extra R^-1 per factor (its "drift"), corrected once when the
  value is read; R differs between the AVX-512 and scalar engines, so never combine products from
  different engines. `EncryptedTally.AddBallots` and `BallotAggregationVerification.Verify` take a
  `maxDegreeOfParallelism`, as do `TallyGuardian.Commit`/`Respond`, `TallyAdmin.Decrypt`/`Combine`
  and `TallyDecryptionVerification.Verify`; pass it through so that `egperf --parallelism 1` stays
  a true single-threaded baseline.
- `TallyAdmin.Combine` recovers each plaintext count with `BoundedDiscreteLog`, baby-step
  giant-step over `[0, bound]` with one table shared by every choice: about
  2·sqrt(choices x bound) multiplies for the whole tally. The bound is the largest
  `EncryptedAggregateChoice.MaximumCount` = its contest's `EncryptedAggregateContest.CastWeight` (the
  sum of W over the cast ballots that list the contest) times the field's own bound
  (`EncryptedTally.MaximumOptionValue`: min(R, L) for an option, 1 for an indicator, L for the
  undervote difference count, `WriteInFieldCount` for the write-in count), not `BallotsCast`, which ignores weights and R.
  The cast weight is published with the encrypted tally (the record's `encrypted_tally_contest.cast_weight`),
  so a tally read back from a record decrypts (S10a; it failed closed with "not in [0, 0]" before), and
  Verification 9 compares it with the recomputed one (`"9.structure"`, after 9.A/9.B). Until then
  it is a claim: a tally read from a record is decrypted only through `VerifyAggregatedAsync`'s
  `VerifiedAggregate` (the console does). The mapper clamps a weight to `long.MaxValue`, `MaximumCount`
  saturates at `long.MaxValue` instead of wrapping, and `Combine` refuses a bound that is negative
  or above `int.MaxValue` with `TallyDecryptionException`. It and the batched inverse
  (`ModInverseVariableTime`, a binary extended GCD over stack limbs: the division-based form
  allocated 2 MB per call, which `compare`'s allocation gate flags) are **variable-time**, which
  is safe only because the counts, the combined partial decryptions and T are published; never use
  either on a secret. Everything a guardian does with u_i or z_i (`Commit`, `Respond`) goes through
  the constant-time `MontgomeryModP.PowModP`.
- The tally-decryption test seams are internal: `TallyGuardian.NonceSourceForTesting` (the KAT
  drives the whole protocol with the oracle's u_i), `TallyGuardian.PartialDecryptionTamperForTesting`
  (a guardian consistent about a wrong M_i, the delta-shift attack) and
  `TallyAdmin.VerifyBeforePublishing` (false shows Verification 10.B catching what the
  administrator's own check would have). For contest data the first two are called with ind_o = 0,
  and Verification 12.B catches the wrong m_i; for a ballot nonce the tamper seam is called with (0, 0, m_i); `BallotEncryptor.ContestDataProofNonceForTesting`
  fixes the eq. (69) nonce u so the KAT reproduces C_2. The egperf `VerifyDecryption` phase runs Verifications 10
  and 11 after a successful decryption when `tallyVerification` is on.
- Manifest contest and option `Index` values are the 1-based list positions (§3.1.3): the first contest is 1,
  and the first option of each contest is 1; a supplemental field's index continues after the options.
  `Manifest.Validate()` enforces this, along with unique contest ids, unique option and field ids within a
  contest, at most one supplemental field per kind, a write-in field count of at least 1 where the write-in
  count is declared and a declared write-in count wherever write-in fields are offered (Q13), R >= 1 (§3.1.3: "a positive integer") and L >= 1 (with
  L = 0 every selection overvotes), and unique ballot style ids. It throws `InvalidManifestException`. It runs
  when an `EncryptionRecord` is built (including deserialization), in the `BallotEncryptor` constructor and in
  `PreEncryptionPrimitives.GenerateContests` (the per-contest pre-encryption primitives check the option
  numbering of the contest they are given). Verifications 6, 7, 8 and 16 deliberately do not call it per ballot (it is
  O(manifest)); they trust the record's construction-time check. Every hand-built test manifest must follow it. It does not check that a
  ballot style's contest ids exist; perf tests rely on that failing later. (Verification reports it per ballot,
  through `BallotStructure`, as `N.structure`.)
- Contest hashes and confirmation codes are taken in manifest order (eqs. 70/71): options in option-index order,
  then the declared supplemental fields in manifest order, contests in contest-index order. The order the plaintext ballot lists them in does not matter.
  `BallotEncryptor.Encrypt` emits `EncryptedBallot.Contests`, each contest's `Choices` and its `SupplementalFields` in that canonical order.
  Verification 8 sorts by manifest index before recomputing, so a stored ballot's list order is irrelevant there
  too.

  the vectors to make a test pass. Families the library cannot express yet are listed in

- **Pre-encrypted ballots** (§4; G31, S9; scope per user decision Q35, S9c): this library implements the
  **primitives** of pre-encryption and its verifications only. The §4.2 encrypting tool and the §4.3 recording
  tool (drawing id_B and ξ_B, discarding a ballot whose short codes repeat, obtaining ξ_B, choosing and padding
  the combined vectors, regenerating a printed ballot to check it, what to publish) are out of scope: S9c
  removed `BallotPreEncryptor`, `BallotRecordingTool`, the guardians' pre-encrypted nonce decryption with its
  issued list and once-only state, and the console demo. `PreEncryptionPrimitives` (in `PreEncryption`) holds
  the formulas a tool builds on: `GenerateSelection`/`GenerateContest`/`GenerateContests` (the vectors that
  H_I and ξ_B determine: nonces ξ_{i,j,k} of eq. 121, selection and null-vector hashes of eqs. 113/114, short
  codes Ω(ψ), the eq. 115 contest hash over all m + L hashes; options in index order, the l-th null vector's
  index m + l; every encryption carries its nonce in `EncryptionNonce`, which no serializer writes;
  `GenerateContests` validates the manifest and requires Ω; `GenerateSelection`, `GenerateContest` and
  `ProveCombinedContest` take a bare `Contest`, so they check its own option numbering, at least one option
  (`ArgumentException`) with indices 1..m in list order (`InvalidManifestException`), but cannot check its
  contest index against the manifest), `HasUniqueShortCodes` (§4.1.5), `Combine` (§4.3:
  componentwise product mod p, nonces summed mod q) and `ProveCombinedContest` (eq. 59 per component over
  0..R, eq. 62 over 0..L, keyed with H_I, through the shared `BallotEncryptor.GenerateProofs`; an internal
  overload takes the KAT's proof-nonce seam). The rest is public already: `PreEncryptionNonce`,
  `SelectionHash`, `ContestHash.ForPreEncryptedContest`, `ConfirmationCode.ForPreEncryptedBallot`,
  `VotingDeviceInformationHash.ForPreEncryptedBallots`, `ChainingField.ForPreEncryptedBallots` (and its
  initial/closing forms), `DeviceChain.ForPreEncryptedBallots`, `BallotNonceEncryption`, `HashTrimming`.
  Tests build ballots and records with the test-only `PreEncryptedBallotFixtures` (Testing.Common), which
  takes ξ_B from the caller and makes the choices the verifications expect (exactly L combined vectors, an
  undervote padded with the first null vectors, Q27). The published records stay: a cast pre-encrypted ballot
  is a standard `EncryptedBallot` (status cast, weight 1) whose `Contests` hold the combined vectors with
  standard proofs, eq. (115) contest hashes, the eq. (116) confirmation code and the pre-encrypted B_C, and
  whose `PreEncryptedContests` carry the §4.4 extras (all m + L selection hashes strictly ascending, the L
  selected vectors sorted by hash with short codes, never an option label or a nonce; in the record the
  `pre_encrypted_cast_ballot` item). So the tally and Verifications 5-7 and 9-11 take it
  like any ballot; Verification 6 also checks 6.A on every entry of every selected vector (p.64: "including all
  individual selection encryptions within the selection vectors"; two non-members can multiply to a member),
  and `Verify(PreEncryptedUncastBallot)` does the same for every vector of an uncast ballot. Verification 8 refuses it (`"8.structure"`, p.64). Verifications 15, 16 and 17 have cast
  overloads, after `BallotStructure.RequirePreEncryptedCast` (`"N.structure"`); a pre-encrypted record must be
  cast (`"15/16/17.structure"`), and the challenged-ballot path (guardians, administrator, V13, V14) refuses
  one. 15.A is applied for every L. An uncast ballot is published as `PreEncryptedUncastBallot`: the ballot,
  the released ξ_{i,j,k} per vector, and ξ_B optionally (§4.4 vs §4.3; Q28). V18 recomputes every encryption
  from the released nonces with δ from the vector's label. It compares each with the published one (18.A; a
  library hardening: χ sorts the hashes, so a device that prints two honest vectors beside each other's
  options changes no hash and no H_C), and checks the nonces against a released ξ_B (18.A). It hashes all
  m + L vectors (eq. 115, not 18.4's m_i). V19 checks labels (null vectors carry none). `BallotStructure`
  requires the manifest to name Ω for a `PreEncryptedBallot`, and each vector's index to be eq. (121)'s
  (option index; m + l for the l-th null vector). The record writes an uncast ballot as its printed item (compact
  exactly when ξ_B is released) plus a final-phase `uncast_nonce_release` (`UncastMapper`; user decision R-1).
